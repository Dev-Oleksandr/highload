## 1. Архітектура

### Scheduler. 
Курсор по полю next_check_at у БД відбирає «прострочені» сутності та кладе задачі в чергу (Kafka / SQS — залежно від наявної інфраструктури; критичні вимоги — durability і ретраї). Окремі черги за типами (appstore_check, googleplay_check, adstxt_fetch), щоб інцидент одного конвеєра не блокував інший. Задачі ідемпотентні: ключ = (entity_id, planned_date), семантика at-least-once.

### App Store worker. 
Офіційний iTunes Lookup API (…/lookup?bundleId=…): повертає sellerName і sellerUrl, підтримує пакетні запити (десятки–сотні ID за виклик). Свідомий вибір API замість скрапінгу — стабільний контракт, мінімальний анти-бот ризик; половина парку закривається «дешево».

### Google Play worker.
HTML-скрапінг play.google.com/store/apps/details?id=…, парсинг embedded JSON. Саме сюди йде бюджет проксі та уваги: ротація IP, токен-бакети лімітів у Redis, чесний User-Agent, backoff при 429. Розрізняємо 404 (застосунок видалено → статус removed, зупинка перевірок) і 429/блокування (тимчасово → ретрай).

### ads.txt worker.
Нормалізує developer URL до кореневого домену (eTLD+1 через Public Suffix List, зрізання www/m), робить GET https://{domain}/app-ads.txt. Умовні запити (ETag / If-Modified-Since): переважна більшість файлів не змінюється щодня, тож 304 — найдешевший сигнал «без змін». Обов'язкова валідація відповіді: парковані домени часто віддають 200 з HTML — це трактується як «файлу немає», а не як контент. Ліміт розміру відповіді, обробка редиректів за специфікацією IAB (зокрема не більше одного редиректу за межі кореневого домену).

### Storage.
PostgreSQL — джерело правди для метаданих і розкладів. S3 — raw-снапшоти файлів; нова версія пишеться лише при зміні content-hash. Опційно ClickHouse для розпарсених рядків (ad system domain, account_id, DIRECT/RESELLER), якщо знадобиться аналітика на мільярдах рядків; на старті парсимо тільки при зміні файлу.

## 2. Ключові рішення

Дедуплікація за доменом. app-ads.txt належить домену, а не застосунку. Модель: app → (many-to-one) → domain, причому зв'язок змінний — weekly-джоб може перевісити застосунок на інший домен. Без цього довелося б робити всі запити на одні й ті ж домени, замість унікальних запитів по кожному домену без дублюючих запитів.

Офіційне API там, де воно є; HTTP-first, headless — лише як fallback. App Store: itunes.apple.com/lookup?bundleId=… віддає JSON із sellerUrl, artistName, trackId — без парсингу HTML, стабільно й дешево. Google Play офіційного API для чужих застосунків не має, тому парсимо play.google.com/store/apps/details?id=…&hl=en&gl=US, але не через CSS-селектори, а з вбудованого JSON (AF_initDataCallback) — він змінюється значно рідше за верстку.

Черга + next_check_at, а не cron. Cron по таблиці на 50 млн рядків не працює. Планувальник щохвилини вибирає батч WHERE next_check_at <= now() (partial index, партиції за hash(bundle_id) для паралельного полінгу) і пушить у Kafka. Дата наступної перевірки розмазується детерміністичним джитером hash(id) % interval, щоб не було піку опівночі. Воркери stateless, автоскейл за лагом черги.

Умовні запити (conditional GET). Для щоденної перевірки зберігаємо ETag / Last-Modified і шлемо If-None-Match / If-Modified-Since. 80–90% відповідей — 304 без тіла: економія трафіку, часу і всього етапу парсингу. Де 304 не підтримується — порівнюємо SHA-256 контенту. Новий snapshot створюємо лише при зміні хеша, тож щоденна перевірка не роздуває сховище.

Ізольований egress-шар. Проксі-пул (датацентрові + резидентні як fallback), per-provider token bucket, AIMD-throttling за часткою 429/403, circuit breaker на пул і на окремий хост. Винесено в окремий сервіс, щоб політики лімітів змінювались конфігом у рантаймі — під час бану реагувати треба хвилинами, а не релізом.

Розділення сховищ за характером доступу. Postgres — стан і метадані (транзакційність, індекси планувальника). S3 — сирі файли, content-addressed за хешем (дедуп версій, повний аудит). ClickHouse — розпарсені рядки (~1 млрд) для запитів верифікації та аналітики. Назовні — Kafka-фід змін (app.publisher.changed, appads.updated) плюс REST для точкових запитів.

## 3. Edge case

Адаптивний розклад замість жорсткого cron. next_check_at + fetch_interval на рівні сутності: стабільні 404/timeout деградують daily → weekly → monthly (через fail_count), нові чи змінені сутності перевіряються негайно. Це зрізає «хвіст» мертвих і паркованих доменів, яких на такому обсязі багато, і вивільняє бюджет під живі.

Стійкість до збоїв. Retry з exponential backoff + jitter; DLQ для задач, що стабільно падають (ручний розбір). Парсер Google Play версіонується, canary-набір сторінок проганяється постійно: падіння parse success rate — алерт про зміну верстки ще до деградації всього конвеєра.

Валідація за IAB-специфікацією: Content-Type: text/plain, не більше одного редіректу за межі кореневого домену, стрімінг із cap ~10 МБ, підтримка директиви subdomain=. Soft-404 (HTML із кодом 200) — найчастіший клас хибнопозитивів: без перевірки типу контенту в базу поллється сміття.

Developer URL веде на facebook.com / linktr.ee / парковку — блок-лист соцмереж і хостингів; такий застосунок отримує статус «не верифікується», а не «помилка».

Permanent vs transient: 404 / 410 / NXDOMAIN → зміна статусу і рідша перевірка; 5xx / timeout / 429 → ретраї з експоненційним backoff, після N поспіль — карантин і DLQ. Змішувати їх не можна: інакше тимчасовий збій хостера «вб'є» тисячі валідних доменів.
